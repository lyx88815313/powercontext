### 1.4 重试机制（本次未触发，但已实现）

若补丁无法解析 / 无法应用 / 测试未通过，模块会把失败原因（以及测试输出尾部）
作为"上一次尝试的失败反馈"回灌给模型重新生成，并**回滚**工作区到补丁前状态，
默认最多 3 次。开发过程中确实触发过一次：模型第一版补丁的 hunk 起始行号与文件
不一致，模块定位到原因后把"上下文不匹配"的具体行回灌给模型，模型重出了一版
可通过的补丁；随后把补丁应用策略改为与 `git apply` 一致（允许 hunk 整体偏移，
但上下文必须逐行一致），该问题不再出现。

### 2.3 检索（构造上下文）

实际执行的 SQL（全文检索，节选自 **`evidence/db-queries.log`**）：

```sql
-- 建表 / 索引
CREATE TABLE IF NOT EXISTS spec_item (
    spec_id      VARCHAR(128)  NOT NULL,
    item_id      VARCHAR(128)  NOT NULL,
    version      VARCHAR(32)   NOT NULL,
    title        VARCHAR(512)  NOT NULL,
    body         TEXT          NOT NULL,
    body_tokens  TEXT          NOT NULL,
    tags         TEXT,
    source_path  VARCHAR(512)  NOT NULL,
    content_hash VARCHAR(64)   NOT NULL,
    updated_at   DATETIME      NOT NULL,
    PRIMARY KEY (spec_id, item_id)
);
CREATE FULLTEXT INDEX ft_spec_item_tokens ON spec_item (body_tokens)
    WITH PARSER space PARSER_PROPERTIES=(min_token_size=1, max_token_size=84);

-- 任务检索（code_unit / test_unit 同构）
SELECT *, MATCH(body_tokens) AGAINST(%s) AS relevance
FROM spec_item
WHERE MATCH(body_tokens) AGAINST(%s)
ORDER BY relevance DESC
LIMIT 12;
```

本次三类资料的检索方式全部是 `fulltext`（未降级到 LIKE 兜底）：

| 表 | 检索方式 | 命中 |
| --- | --- | --- |
| `spec_item` | fulltext | 8 |
| `code_unit` | fulltext | 11 |
| `test_unit` | fulltext | 14（19 个用例单元里命中 14 个） |

上下文 digest：`fff5ca481740789049e650e65506e2d7eacb533d3fdb368672dfface8214e151`

记录：**`evidence/context.json`**（含 `db_evidence` 段：查询 token、逐表命中、
行数、检索方式、必需来源校验结果）、**`evidence/db-queries.log`**（表结构、索引、

| 鉴权 | 默认关闭（仅监听回环地址） |

### 3.2 状态写入（三写）

一次任务状态写入会落三处：

| # | 接口 | 作用 | 证据 |
| --- | --- | --- | --- |
| 1 | `POST /v1/sources/content` | **字节级快照**：任务状态 JSON 原文（真相来源） | `evidence/state_save.json` 的 `snapshot_source_id` |
| 2 | `POST /v1/work/outcomes/record` | **结构化任务结果**：objective / observations / checks / remaining_work（PowerContext 原生任务语义） | `evidence/state_save.json` 的 `outcome_source_id` |
| 3 | `POST /v1/memory/remember` | **可检索记忆条目**：kind=`sdd-task-state:TASK-001`，文本里带快照 id 作为指针 | `evidence/powercontext_requests.jsonl` |

> 实现要点：PowerContext 的 `TaskOutcome` 要求 `observations` 至少一条、
> 文本字段必须已 trim、`produced_artifacts` 只能引用真实存在的构件；
> 模块据此把改动文件记在 `observations`、`produced_artifacts` 留空。

### 3.3 状态复用（跨进程读回）

| 阶段 | 证据 | 结果 |
| --- | --- | --- |
| 流水线开始时（**空状态**） | `evidence/state_before.json` | `found=false`、`memory_entries=0` → 从空状态开始 |
| 流水线结束（写入状态） | `evidence/state_save.json` | 三写全部成功（HTTP 202 / 202 / 200） |
| **重启模块后**（全新进程） | `evidence/state_after_restart.json` | `present=true`、6 条已完成事项、2 条验证结果、`context_digest=fff5ca48…` |

读回路径：先 `POST /v1/memory/entries/list` 找到本任务最新的 active 记忆条目
（按指针里的 `updated_at` 取最新）→ 取出 `snapshot_source_id` →
`GET /v1/scopes/{scope_id}/sources/content/{source_id}` 回读**字节级原文** →
解析成任务状态。

### 3.4 请求审计

本次会话对 PowerContext 的全部 HTTP 调用（方法、URL、状态码、耗时、请求体摘要）
逐条记录在 **`evidence/powercontext_requests.jsonl`**（本次运行 6 条；每次运行重新生成，互不混杂）。
